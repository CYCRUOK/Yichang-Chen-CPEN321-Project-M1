1.6 Button 3 – Timer and "While You Waited"

The user sets a timer in minutes and seconds. The countdown is derived from a fixed deadline (not from counting ticks), so it stays exact across rotation and while the app is in the background. When it goes off the phone vibrates, posts a "Time's up!" notification (Android 13+ requests the notification permission on the first Start), confetti falls over the screen and a "While you waited N s…" summary appears, telling the user what happened in the world during exactly the time they waited:

  • The International Space Station – its live position is fetched from https://api.wheretheiss.at when the timer starts and again when it fires; the app computes the great-circle distance flown (haversine at the ISS altitude) and draws both fixes and the hop on a mini equirectangular world map with coarse continent outlines drawn from an in-app polygon table.
  • Earth travelled 29.78 km/s × t along its orbit.
  • Light travelled 299 792 km/s × t, expressed in Moon round trips.
  • Whether the sunlight that left the Sun at Start (8 min 19 s away) has arrived yet.
  • Approximate heartbeats, blinks and babies born worldwide.

If the ISS API is unreachable the card degrades gracefully and the locally computed facts are still shown. The surprise therefore combines an external API, the app's own computation, sensors/OS features (vibration, notifications) and an animation, and its content is tied to the timer duration itself.

1.7 Limitations

  • Google sign-in works only for APKs signed with a registered key (submitted APK, or the developer's debug key); see 1.3.
  • The name shown for the signed-in user is the Google account's profile name (given + family name). If the account has no family name set, only the given name is displayed.
  • The ID token is not verified server-side; the three information APIs are public. This is acceptable for M1 but not for the project.
  • Client IP shows the device's private Wi-Fi/mobile address (IPv4 preferred, IPv6 otherwise), not its NAT public address.
  • The pixel stream has no "new image" marker; the canvas is cleared when the server pauses for more than 2 s. Joining mid-image shows a partial first image until the next pause.
  • The timer runs inside the app process; if Android kills the app in the background, the alert is lost (no AlarmManager / foreground service).
  • The ISS card needs internet; the ISS distance is an estimate from two position samples (or speed × time if only one sample was obtained).
  • The continent outlines on the mini map are deliberately coarse hand-simplified polygons.
  • The development machine has hardware virtualization disabled in its BIOS, so the Pixel 9 API 36 emulator could not be run locally; testing was done on a physical Android 15 device plus a successful API 36 build. [Update this line if you enable VT-x and run the emulator before submitting.]
  • The certificate is bound to 8-229-19-28.sslip.io; if the VM's static IP ever changed, the domain, certificate and API_BASE_URL would all have to be regenerated.

3. AI Use Reflection

Drafted from the actual development session; please edit so it reads in your own words and reflects your own experience.

Task A – Implementing the back-end WebSocket relay and the live pixel-art screen

Task. Relay the course server's pixel stream through my own Node.js back-end to the Android app and paint each pixel live on a 16×16 grid.

Tools. Claude Code (Anthropic) running the Claude Opus 5 model inside the Claude desktop app, with access to my terminal, the repository and the connected phone through adb.

Strategy. Before writing any code I had the assistant probe the course server with a throw-away script so that we knew the real behaviour (one pixel every 50 ms, 256 pixels per image, a 5-second pause, no "clear" message, a valid Let's Encrypt certificate). The design followed from those facts: the relay forwards messages byte-for-byte, and the client clears the canvas when it detects a pause longer than 2 s. I asked for the relay to be written against an injectable upstream so the tests could run against a fake WebSocket server instead of the internet; the assistant wrote the fake, the reconnect test and the fan-out test, then verified the real path end-to-end with a probe client and, on the Android side, by installing the app and screenshotting the butterfly assembling on my phone.

Advantages. The speed of going from "unknown protocol" to "verified working on the device" was the biggest win – measuring the server first avoided guessing, and the assistant produced the boilerplate (OkHttp listener → Flow, ViewModel state, Canvas drawing, Jest tests with fake servers) in minutes. Having it run the tests and look at screenshots itself meant bugs (e.g. a flaky navigation assertion during the 20 Hz repaint) were found and fixed before I saw them.

Disadvantages. Generated code is easy to accept without fully reading it; I had to deliberately review the relay (for example, that it really does not batch or reformat messages, which the assignment forbids) and the gap-detection heuristic, which is an assumption about the server rather than a documented contract. The assistant's first test for the timer also asserted an intermediate state that is never observable with instant fakes – a reminder that AI-written tests can encode the wrong expectation and need the same scrutiny as production code.

Task B – Google sign-in and the release-signing / OAuth setup

Task. Sign the user in with Google using the current Credential Manager API and make it work for both the debug and the release APK.

Tools. Claude Code with Claude Opus 5; Google Cloud Console (done by me by hand).

Strategy. I split the work along the boundary of what the assistant can and cannot do: it wrote the GoogleAuthenticator abstraction, the view model and UI tests driven by a fake authenticator, and it extracted the SHA-1 fingerprints of the debug and release keys with keytool; I created the OAuth clients and consent screen in the console because that needs my Google account. When the release build failed to sign in, the assistant explained that Credential Manager reports an unregistered signing key as a plain "cancelled" and improved the error message so the cause is visible to graders.

Advantages. The Credential Manager API and the googleid library are recent and their documentation is scattered; the assistant knew the current recommended flow (GetSignInWithGoogleOption, parsing GoogleIdTokenCredential) and the exact console steps, which saved a lot of searching. Wrapping the system dialog behind an interface made the rest of the screen testable without Google.

Disadvantages. The assistant cannot see or drive the Google account picker, so the real sign-in path could only be confirmed manually on my phone; and it could not tell me in advance that the release key needs its own OAuth client entry – we only learned it when the release APK failed. Anything that touches account settings (publishing the consent screen, changing my Google profile name) stays a manual step.

Task C – Cloud deployment with HTTPS/WSS

Task. Deploy the back-end on Google Cloud with a trusted certificate so the app can use HTTPS and WSS without trusting a self-signed CA.

Tools. Claude Code with Claude Opus 5, connected to the VM over SSH with a key generated for that purpose.

Strategy. I created the VM and firewall rules in the console; the assistant wrote two idempotent scripts (cloud-setup.sh: Docker, clone, .env, Compose; cloud-https.sh: nginx + certbot with the WebSocket upgrade) and ran them over SSH, then re-ran the same smoke test script it had used locally against the public URL, checked the certificate chain with openssl, and rebooted the VM to prove the service comes back on its own. Using an sslip.io name avoided registering a domain.

Advantages. The deployment became reproducible code in the repository rather than a sequence of manual commands, and every step was verified immediately (the first Docker build failed because the Windows-generated lock file lacked a Linux-only optional dependency – the assistant diagnosed it from the build log and regenerated the lock file inside the same Node image).

Disadvantages. The assistant had full shell access to the VM; that is convenient but I had to be comfortable with it running sudo and rebooting the machine. Cloud-console steps (billing, firewall rules, static IP) remain manual and were the source of the only misconfiguration we hit (port 3000 not opened – harmless because only 443 is used in the end). Line-ending problems (CRLF from Windows breaking a bash script) also cost a couple of iterations.
